# 验收标准

> 状态：Accepted
>
> 候选基线：v1.0
>
> 说明：详细 Given/When/Then 场景见 [验收场景](acceptance-scenarios.md)。

## 产品验收

### AC-001 输出完整性

当系统成功生成旅行计划时，结果必须包含每日行程、预算汇总、约束检查报告和动态信息来源。

### AC-002 预算约束

- 参与预算范围的已知与估算费用超过用户总预算时，预算检查必须返回 `FAIL` 并触发重新规划。
- 预算剩余不足总预算的 10% 时，预算检查必须返回 `WARNING`。
- 预算明确不包含住宿时，住宿费用必须展示，但不得参与预算上限和剩余预算计算。
- 未知费用必须单独展示，不得按零费用处理。

### AC-003 时间约束

- 同一日期内的时间线项目不得重叠。
- 交通和用餐时间必须计入日程。
- 活动时间不得超出用户设定的每日时间范围。
- 已知开放时间的活动不得安排在闭馆时段。

### AC-004 行程强度

停留时间不少于 60 分钟的景点或体验视为主要活动：

- 轻松节奏每天最多安排 3 个主要活动。
- 适中节奏每天最多安排 4 个主要活动。
- 紧凑节奏每天最多安排 5 个主要活动。

### AC-005 路线约束

普通城市行程中，连续地点间的预计交通时间原则上不得超过 60 分钟。用户指定的必去地点或无法避免的情况可以例外，但系统必须说明原因并返回 `WARNING`。

### AC-006 偏好与强制约束

- 每天没有符合用户核心兴趣的活动时，系统必须返回 `WARNING` 并说明候选不足。
- 用户指定的必去地点缺失时，系统必须返回 `FAIL`。
- 用户指定避开的地点出现时，系统必须返回 `FAIL`。

### AC-007 天气适配

- 普通降雨时，系统应优先替换不合适的室外活动；无法替换时返回 `WARNING`。
- 严重天气预警下安排明显不安全活动时，系统必须返回 `FAIL`。

### AC-008 信息可信度

天气、开放时间、路线和价格等动态信息必须包含来源和查询时间。缺少可靠信息时必须标记为 `UNKNOWN`，不得编造。

### AC-009 局部调整

当用户仅要求调整指定日期时，系统应保留其他日期的计划；只有在满足全局硬性约束所必需时才可联动修改，并必须说明原因。

### AC-010 工具失败

外部工具失败时，系统应返回可识别的失败或降级结果，不得以模型生成的虚构数据代替工具结果。

### AC-011 统一检查状态

约束检查只使用以下状态：

- `PASS`：满足约束。
- `WARNING`：计划可用，但存在需要用户注意的问题。
- `FAIL`：违反硬性约束，需要重新规划。
- `UNKNOWN`：缺少可靠信息，需要用户确认。

### AC-012 自动重规划上限

- 一次规划任务最多生成 3 份完整候选计划。
- 每次自动重规划必须记录触发原因和采取的修改动作。
- 第 3 份候选计划仍然违反硬性约束时，系统必须停止自动规划并进入 `NEEDS_USER_INPUT`。
- 系统不得自行放宽用户已经确认的硬性约束。

### AC-013 任务结果状态

- 已知硬性约束全部通过时，任务可以进入 `COMPLETED`。
- 只有软性约束警告时，任务仍可进入 `COMPLETED`。
- 路线、天气、价格或开放时间等重要信息无法确认时，任务必须进入 `PARTIAL`。
- 无法生成可解析、可校验的候选计划时，任务必须进入 `FAILED`。
- 用户取消任务后，任务必须进入 `CANCELLED`，不再执行未开始的后续步骤。

### AC-014 匿名保存失败

匿名保存失败不得改变已经确定的规划结果状态。系统必须提示行程未保存、不返回行程 ID，并允许用户重新尝试保存。

### AC-015 旅行需求校验

- 过去的开始日期必须被拒绝。
- 结束日期早于开始日期必须被拒绝。
- 同时提供的结束日期与天数不一致时必须请求确认。
- 旅行天数不在 1～3 天范围内必须被拒绝。
- 同行人数不在 1～8 人范围内必须被拒绝。
- 总预算不大于 0 必须被拒绝。
- 缺少预算是否包含住宿的信息时，不得进入规划确认状态。
- 缺少兴趣偏好时，不得进入规划确认状态。
- 用户未提供每日时间时，摘要必须展示默认的 `09:00` 至 `21:00`。

### AC-016 规划前确认

- 必填信息完整后，系统必须展示结构化需求摘要、默认值和不确定项。
- 用户确认前，系统不得开始正式规划。
- 用户修改摘要后，系统必须重新校验并再次等待确认。

### AC-017 时间线与版本

- 交通、用餐和休息必须作为独立时间线项目。
- 同一天时间线项目不得重叠。
- 初始计划版本必须为 1。
- 成功修改后的版本必须等于上一版本加 1。
- 修改失败时不得覆盖上一可用版本。

### AC-018 匿名行程访问与删除

- 匿名行程 ID 必须不可预测且不可枚举。
- 不存在、已过期和已删除的 ID 必须返回相同外部错误。
- 删除成功后，该 ID 不得再返回行程内容。
- 默认保留期限必须在保存时展示。

### AC-019 过期来源

- 重新打开历史行程时，过期或时效未知来源必须被标记。
- 仅查看历史版本时可以保留原数据，但不得把过期信息显示为最新事实。
- 修改受影响行程时，系统必须尝试重新查询相关动态信息。

### AC-020 并发版本冲突

- 局部修改请求必须携带其基于的版本号。
- 请求版本不是最新版本时，系统必须返回 `VERSION_CONFLICT` 和最新版本号。
- 发生冲突时不得创建新版本，也不得覆盖当前最新版本。

## 工程质量门禁

- 所有 `Must` 用户故事至少有一个端到端验收场景。
- 核心确定性模块行覆盖率不低于 90%，项目整体行覆盖率不低于 80%。
- 格式检查、静态检查、类型检查、单元测试、集成测试、密钥扫描和 Agent 回归评测全部通过。
- 真实工具与模拟工具通过同一组契约测试。
- 不存在未处置的高严重度依赖或代码安全问题。

## Agent 评测门禁

- 评测数据集、指标和回归规则见 [Agent 评测需求](evaluation-requirements.md)。
- 任意可重复的硬性安全门禁失败时不得发布。
- 大模型评审只能作为补充，不得作为安全、权限和确定性约束的唯一判据。
