# 业务规则

> 状态：Accepted
>
> 阶段：Sprint 0

业务规则描述跨功能复用、可独立验证的产品约束。每条规则将在需求追踪矩阵中关联功能需求、验收标准和测试。

## BR-001 首次规划确认

首次正式规划前，系统必须向用户展示结构化需求摘要、使用的默认值和仍然存在的不确定项。只有用户明确确认后，系统才能进入正式规划。

用户修改需求摘要后，系统必须重新执行完整性与合法性校验，并再次获得确认。

## BR-002 自动重规划上限

系统最多生成 3 份完整候选计划，包括初始计划和最多 2 次自动重规划。

每次重规划必须针对上一轮明确的失败原因进行调整，不得原样重试，也不得自行放宽用户确认的硬性约束。

第 3 份候选计划仍然违反硬性约束时，系统必须停止自动规划，进入 `NEEDS_USER_INPUT` 状态，展示未解决的约束和可选择的调整建议。系统可以展示最接近要求的候选计划，但必须明确标记该计划尚未通过硬性约束检查。

## BR-003 硬性约束

违反以下任意约束时，检查结果为 `FAIL`，系统必须重新规划或请求用户调整需求：

- 目的地、日期、人数等必填数据不合法
- 行程不在第一版支持的 1～3 天范围内
- 已知费用超过用户确认的预算上限
- 时间线项目重叠
- 时间线项目超出用户确认的每日可用时间
- 活动安排在已知闭馆时段
- 缺少用户确认的必去地点
- 出现用户明确要求避开的地点
- 违反用户明确的行动、健康、饮食或其他可达性限制
- 轻松、适中、紧凑节奏分别超过每天 3、4、5 个主要活动
- 严重天气预警下安排了明显不安全的活动

系统不得自行放宽用户确认的硬性约束。两个硬性约束互相冲突时，系统必须进入 `NEEDS_USER_INPUT`。

## BR-004 软性约束

以下约束用于改善计划质量。单项违反时检查结果为 `WARNING`，不单独触发整份计划失败：

- 尽量保留总预算的 10% 作为预留金额
- 连续地点间交通时间原则上不超过 60 分钟
- 每天尽量包含至少一个符合核心兴趣的活动
- 地点尽量按区域聚类
- 普通降雨时优先安排室内活动
- 用餐区域尽量靠近前后活动
- 尽量减少重复类型的景点

## BR-005 约束冲突优先级

系统处理约束冲突时使用以下优先级：

```text
安全与可达性
→ 用户明确禁止事项
→ 日期和可用时间
→ 预算上限
→ 必去地点
→ 旅行节奏
→ 兴趣偏好
→ 路线便利性
→ 预算预留
```

高优先级约束优先于低优先级约束。两个硬性约束冲突时，系统不得自行选择，必须说明冲突并请求用户决策。

## BR-006 规划任务状态

规划任务只使用以下业务状态：

- `COLLECTING_REQUIREMENTS`：正在收集和补全需求
- `AWAITING_CONFIRMATION`：需求完整，等待用户确认
- `PLANNING`：正在获取数据并生成初始计划
- `REPLANNING`：正在根据失败原因自动调整计划
- `COMPLETED`：已生成可用计划，已知硬性约束全部通过
- `PARTIAL`：已生成计划，但部分重要信息无法确认
- `NEEDS_USER_INPUT`：硬性约束冲突，需要用户决策
- `FAILED`：无法生成可用计划
- `CANCELLED`：用户主动取消任务

存在软性约束警告不影响任务进入 `COMPLETED`。路线、天气、价格或开放时间等重要信息无法确认时，任务必须进入 `PARTIAL`，对应检查项标记为 `UNKNOWN`。

大模型服务持续不可用、地点工具没有任何可用候选、目的地无法识别、所有候选计划无法解析校验或出现不可恢复的数据一致性错误时，任务进入 `FAILED`。

匿名保存失败不改变规划结果状态，但系统必须提示行程未保存并允许重新保存。

允许的状态转换如下：

| 当前状态 | 允许的下一状态 |
| --- | --- |
| `COLLECTING_REQUIREMENTS` | `AWAITING_CONFIRMATION`、`FAILED`、`CANCELLED` |
| `AWAITING_CONFIRMATION` | `COLLECTING_REQUIREMENTS`、`PLANNING`、`CANCELLED` |
| `PLANNING` | `REPLANNING`、`COMPLETED`、`PARTIAL`、`NEEDS_USER_INPUT`、`FAILED`、`CANCELLED` |
| `REPLANNING` | `REPLANNING`、`COMPLETED`、`PARTIAL`、`NEEDS_USER_INPUT`、`FAILED`、`CANCELLED` |
| `COMPLETED`、`PARTIAL`、`NEEDS_USER_INPUT`、`FAILED`、`CANCELLED` | 无 |

进入结果状态后，当前任务不可重新打开。用户修改需求、继续调整 `PARTIAL` 计划或处理 `NEEDS_USER_INPUT` 时，系统创建关联到原任务的新任务，不得把原任务状态改回执行中。

## BR-007 第一版输入边界

- 行程目的地为国内单个城市。
- 行程天数为 1～3 个自然日。
- 同行人数为 1～8 人。
- 货币只支持人民币。
- 界面与行程内容只支持简体中文。
- 日期和时间使用中国标准时间解释。

超出以上范围的请求不得静默截断或自动改写，系统应明确说明当前版本的支持边界。

## BR-008 日期计算

- 开始日期不得早于当前日期。
- 结束日期不得早于开始日期。
- 用户可以提供“开始日期和结束日期”，也可以提供“开始日期和天数”；系统必须推导另一个值。
- 用户同时提供结束日期和天数但两者不一致时，系统必须请求确认，不得自行选择。
- 开始日期和结束日期都计入旅行天数。
- 超出天气服务预测范围不视为非法请求，但天气状态必须标记为 `UNKNOWN`。

## BR-009 预算语义

- `budget_total` 表示所有同行者在整个行程中的总预算。
- 用户必须明确预算是否包含住宿。
- 住宿费用始终单独展示；预算不包含住宿时，住宿费用不参与预算上限和剩余预算计算。
- 预算必须大于 0。
- 金额以人民币元展示，保留到分。
- 金额计算必须使用十进制定点规则，不得因二进制浮点误差影响约束判断。

## BR-010 默认每日时间

用户未指定每日活动时间时，系统使用 `09:00` 至 `21:00`，并在需求摘要中明确展示该默认值。

每日结束时间必须晚于开始时间。

## BR-011 独立时间线项目

交通、用餐和休息必须作为独立时间线项目进入每日行程，不得只作为景点备注存在。

同一天的所有时间线项目按开始时间升序排列，不得重叠。交通与用餐时间必须计入每日可用时间范围。

## BR-012 行程版本

- 初始可展示计划版本为 1。
- 每次成功的局部或全局修改创建新版本，版本号加 1。
- 已生成的历史版本不可被原地覆盖。
- 修改失败或进入 `NEEDS_USER_INPUT` 时，不创建新的可用版本。
- 每个版本保存对应的需求快照、约束检查和来源记录。

## BR-013 费用确定程度

每项费用必须标记为 `KNOWN`、`ESTIMATED` 或 `UNKNOWN`。

- `KNOWN` 与 `ESTIMATED` 分别汇总。
- `UNKNOWN` 的金额必须为空，不得写为 0。
- 剩余预算只基于已知和估算费用计算，并同时展示未知费用风险。

## BR-014 动态信息来源

天气、路线、价格和开放时间等动态信息必须关联来源与查询时间。

来源过期或时效无法判断时，相关检查不得返回 `PASS`，只能返回 `UNKNOWN` 或基于其他可靠来源重新查询。

## BR-015 动态信息时效

第一版默认最大缓存时效：

| 信息类型 | 最大时效 |
| --- | ---: |
| 天气与天气预警 | 1 小时 |
| 路线时间和距离 | 24 小时 |
| 价格和开放时间 | 24 小时 |
| 地点名称、地址和坐标 | 7 天 |

工具可以配置更短的时效，但不得超过以上上限。超过时效的来源标记为 `STALE`，时效无法判断时标记为 `UNKNOWN`。

仅查看历史版本时可以展示过期信息，但必须明显标记。重新规划受影响内容时必须优先刷新。
