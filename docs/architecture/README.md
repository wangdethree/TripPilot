# TripPilot 架构设计

> 状态：Accepted
>
> 基线：v1.0

本目录记录 TripPilot 从需求到实现之间的架构设计。架构文档描述当前整体设计，重要且需要长期保留原因的选择记录为 ADR。

## 设计目标

- 让 Agent 的行为可控制、可验证、可观察。
- 将大模型的不确定性限制在明确边界内。
- 让确定性业务规则保持可测试和可复用。
- 让模拟工具与真实工具遵守同一契约并可替换。
- 在满足当前规模的前提下保留合理扩展能力。
- 让开发、测试、评测和部署过程可以在简历与面试中清晰说明。

## 设计层次

TripPilot 使用由粗到细的设计顺序：

1. 系统上下文：定义系统边界、用户和外部依赖。
2. 容器设计：定义可独立运行或部署的主要单元。
3. 模块设计：定义服务端内部职责与依赖方向。
4. 工作流设计：定义 Agent 状态、步骤、失败和取消语义。
5. 接口与数据设计：定义 API、工具端口、事件和持久化契约。
6. 部署设计：定义本地、测试、演示和生产式环境的运行方式。

## 架构原则

1. 确定性规则优先使用普通代码实现。
2. 大模型输出在进入业务流程前必须经过结构化校验。
3. Agent 只能通过允许列表中的工具端口访问外部能力。
4. 领域规则不依赖 Web 框架、模型厂商、数据库或外部服务商。
5. 外部依赖失败必须显式返回，不得由模型编造替代结果。
6. 长任务必须支持超时、取消、资源限制和状态追踪。
7. 当前规模优先使用模块化单体，不提前引入微服务或多 Agent。

## 变更规则

架构候选基线确认后，影响模块边界、依赖方向、数据所有权、工作流语义、安全边界或部署拓扑的变更必须更新对应文档，并在必要时新增或替代 ADR。
