# 06：面试与简历表达

## [必须掌握] 30 秒项目介绍

> TripPilot 是一个国内城市自由行规划 Agent。我没有把它做成一次大模型问答，而是用 LangGraph 构建了带确认边界和最多三次候选的有限状态图。模型只做需求提取与候选组合，预算、时间和来源由确定性领域规则检查。项目提供 Fake 与 OpenAI/真实旅行工具适配器、FastAPI 异步任务 API、React 前端、幂等与乐观并发、PostgreSQL 迁移、结构化日志，以及 60 场景版本化评测集。

只有你能解释每个名词对应的代码和权衡后，才使用这段话。

## [必须掌握] 简历项目描述

建议写成 3～4 条，并使用可以由仓库证明的事实：

- 基于 Python、FastAPI、LangGraph 与 React 实现可控旅行规划 Agent，设计需求补全、人工确认、候选生成、确定性约束检查和有限重规划状态图。
- 通过 Ports/Adapters 隔离模型与旅行服务，提供可重复测试的 Fake Adapter，并接入 OpenAI Responses 结构化输出、Open‑Meteo 天气和高德 POI 查询。
- 实现不透明令牌、`Idempotency-Key`、ETag 乐观并发、结构化错误、敏感日志脱敏、SQLAlchemy/Alembic 数据模型与 PostgreSQL Worker 租约。
- 建立 Ruff、mypy strict、pytest 覆盖率门禁、前后端 CI、Docker Compose 和 60 场景版本化 Agent Eval 数据集。

不要写：

- “生产级高并发”——当前没有压测证据；
- “60 个场景全部真实评测通过”——当前自动门禁包含数据集契约与核心离线测试；
- “完整分布式 Worker”——当前演示运行时仍是单进程组合模式；
- “支持全国所有城市可靠规划”——Fake 数据只有成都和西安，真实能力依赖供应商。

## [必须掌握] 5 分钟讲解结构

1. 用户问题：旅行需求不完整，动态数据不可靠，普通聊天结果不可检查。
2. 产品边界：国内 1～3 日自由行，只读查询，不做预订和支付。
3. 核心架构：模块化单体 + 端口适配器 + 有限 Agent 图。
4. 最难问题：概率输出如何满足确定性预算/时间/来源要求。
5. 工程化：异步任务、取消、幂等、版本、迁移、观测、评测。
6. 证据：运行演示、展示一个约束测试、展示 60 场景分类。
7. 反思：持久化 Worker 和完整可执行 Eval 是下一阶段。

## 高频追问

### 为什么使用 LangGraph？

因为流程需要显式状态、条件路由、有限重规划和 Checkpoint 扩展边界。普通函数也能做第一版，但状态图让节点输入输出、终止条件和观测点更清晰。

### 为什么不直接让模型调用所有工具？

旅行规划包含费用、安全和来源边界。工作流决定必需工具和调用阶段，模型只能在允许的结构化输入里选择，能控制权限、费用和终止。

### 如何减少幻觉？

模型只能引用工具返回的地点 ID；动态信息必须携带来源；工具失败映射为未知或失败；最终计划经过领域 Schema 与确定性约束检查。

### 为什么需要 Fake Model/Tool？

单元和回归测试需要稳定、快速、无费用；故障注入也不能依赖真实供应商碰巧出错。真实适配器用于集成与演示，两者共享端口契约。

### asyncio 最容易出什么问题？

忘记 await、无界创建 Task、吞掉取消、错误地重试、共享 AsyncSession、在网络等待时持锁，以及关闭应用时遗留后台任务。

### 项目目前最大的不足？

单进程 Coordinator 尚未替换为完整 PostgreSQL Worker；局部版本修改的 HTTP 设计和数据模型已确定，但可演示版本没有交付完整交互；60 场景目前不是全部自动执行。坦诚说明，并给出迁移方案，比夸大更专业。

## 自测标准

当你能做到以下四件事，项目才真正属于你：

1. 不看文档画出核心数据流和状态图。
2. 独立修改一个领域规则并补齐测试。
3. 解释一个异步故障如何传播到稳定 HTTP 错误。
4. 面对“为什么这样设计”给出替代方案和权衡，而不是只说“企业都这么做”。
