# 产品简介：TripPilot

> 状态：Accepted
>
> 阶段：Sprint 0
>
> 说明：产品定位和第一版范围已确认；具体功能仍以需求与验收文档为准。

## 问题背景

自由行规划需要同时处理用户偏好、预算、日期、地点距离、天气和开放时间等信息。信息分散且约束容易冲突，用户通常需要反复搜索并手工调整行程。

## 产品目标

TripPilot 希望通过受控的 Agent 工作流，组合旅行信息工具，生成可解释、可检查、可局部调整的多日旅行计划。

## 目标用户

计划国内城市 1～3 日自由行、预算有限、不希望花大量时间查询和整理攻略，希望获得个性化且路线合理行程的普通旅行者。

## 核心问题

短途自由行用户需要从分散的景点、天气、路线和费用信息中手工制定行程，既耗费时间，又容易出现路线绕远、行程过满、预算超支和天气不匹配等问题。当条件变化时，用户还需要重新调整整份计划。

## 价值主张

TripPilot 将用户模糊的旅行需求转换为满足预算、时间、距离、天气和个人偏好的可执行行程，并在条件变化时进行局部重新规划。

第一价值是保证行程合理且可调整，第二价值是节省用户搜索和整理攻略的时间。

## 基准使用场景

用户准备和朋友去成都旅行三天，向 TripPilot 提供日期、人数、预算、兴趣偏好和旅行节奏。TripPilot 获取旅行相关信息，生成每日行程，检查预算、天气和路线冲突，并允许用户提出“第二天不要安排室外景点”等局部调整要求。

第一版聚焦目的地内的日程规划，不负责购买出发地到目的地的交通票，不执行酒店、门票、餐厅预订或支付。实时信息需要标注来源和查询时间。

## 第一版核心能力

1. 将用户旅行描述转换为结构化需求。
2. 获取或读取候选景点、天气、路线和费用信息。
3. 根据偏好与约束生成多日行程。
4. 检查预算、时间、距离和天气冲突。
5. 根据检查结果或用户反馈重新规划。

## 非目标

1. 不执行真实机票、酒店、门票购买或支付。
2. 不承诺替代官方渠道提供安全、签证或实时营业信息。
3. 第一版不追求覆盖所有国家、城市和旅行类型。
4. 第一版不采用多 Agent 或微服务架构。

## 数据策略

开发和自动测试使用固定模拟数据，集成测试和演示环境使用真实外部服务。最终演示版本至少接入真实天气和路线或地点服务，同时保留模拟工具用于稳定测试和异常场景评测。

外部工具需要具备参数校验、超时、有限重试、缓存、结构化错误、信息来源和查询时间。服务不可用时应使用缓存或明确降级，不得由模型编造工具结果。
