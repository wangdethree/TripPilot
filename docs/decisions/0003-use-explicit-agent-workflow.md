# ADR-0003：使用显式状态图编排 Agent

> 状态：Proposed
>
> 日期：2026-07-28

## 背景

TripPilot 需要收集并确认需求、调用多个旅行工具、生成候选计划、执行确定性检查、进行最多两次自动重规划，并支持取消、超时、资源预算和故障恢复。

自由运行的 ReAct 循环主要由模型决定下一步工具与终止时机，难以稳定保证确认边界、工具权限、重规划次数、成本上限和任务状态。完全固定的普通流水线又无法根据约束失败原因调整候选计划。

## 决策

TripPilot 使用显式、有限的状态图编排 Agent。

- 工作流代码定义允许的节点、转换、循环次数和终止状态。
- 用户确认是正式规划前不可绕过的暂停点。
- 工作流决定必需工具的调用阶段；可选工具请求仍需经过允许列表、Schema 和资源预算。
- 大模型负责需求理解、候选计划生成和基于结构化失败证据的调整。
- 领域代码负责 Schema 之外的确定性约束、任务状态、版本和最终判定。
- 工作流在关键节点持久化检查点、资源用量和版本信息。
- 取消、超时和资源上限由执行器传播到工作流和端口。
- 自动重规划最多两次，工作流不存在无界模型或工具循环。

## 备选方案

### 自由 ReAct Agent

实现演示较快，模型可以自行选择工具，但行为、调用次数和失败路径更难预测，不适合作为预算和安全边界明确的核心工作流。

### 完全固定的顺序流水线

容易测试和理解，但无法根据预算、路线或时间失败证据选择不同修复策略，Agent 的自适应价值不足。

### 多 Agent 协作

可以把地点、路线、预算拆给不同 Agent，但会增加通信、共享状态、成本、并发和评测复杂度。预算与约束更适合确定性领域服务。

## 影响与后果

正面影响：

- 所有状态、循环和终止条件可以自动测试。
- 可以在节点边界实现取消、超时、检查点和资源控制。
- 模型与工具替换不会改变核心业务状态机。
- 失败案例能够定位到具体节点、模型、工具和约束。
- Agent 仍能根据失败证据进行受控自适应。

需要承担的成本：

- 需要定义工作流状态、节点输入输出和检查点 Schema。
- 新增 Agent 能力时必须显式修改状态图和回归测试。
- 工作流引擎或自研实现必须支持异步、暂停、恢复和可观测钩子。

## 重新评估条件

- 出现无法用有限状态图合理表达的新型开放任务。
- 评测证明受控工具请求显著限制任务完成率。
- 产品范围扩展到多个相互独立、具有不同权限和所有权的 Agent。
- 当前状态图复杂度已经超过单工作流可以维护的范围。
