# ADR-0002：服务端采用模块化单体架构

> 状态：Accepted
>
> 日期：2026-07-28

## 背景

TripPilot 需要同时支持 Agent 工作流、确定性约束、外部工具、行程版本、评测和可观测性。如果没有模块边界，模型调用、业务规则和基础设施代码会相互耦合；如果直接使用微服务，又会增加网络通信、分布式事务、部署和运维成本。

第一版由小规模团队开发，目标并发为 10 个完整规划任务，核心业务属于同一个产品边界，并且行程版本需要原子写入。需求明确不采用多 Agent 协作。

## 决策

TripPilot 服务端第一版采用模块化单体架构，使用同一代码库和发布单元交付。

- 服务端内部按照接口、应用、Agent、领域、工具端口、基础设施和可观测性职责划分模块。
- 领域模块不依赖 Web 框架、大模型 SDK、数据库驱动或具体外部服务商。
- 应用层负责业务用例和事务边界，Agent 工作流负责受控的模型与工具编排。
- 基础设施层实现模型、工具、持久化和遥测端口。
- 模块之间通过显式 Python 接口和 Schema 交互，禁止跨模块直接访问内部实现。
- 运行时可以从同一发布单元启动 API 和任务执行角色；第一版默认在同一服务端实例内运行。
- 客户端可以独立构建和部署，但不改变服务端模块化单体的决策。
- 只有出现经过测量的容量瓶颈、独立扩缩容要求、故障隔离需求或团队所有权边界时，才评估拆分服务。

## 依赖方向

```text
接口层 → 应用层 → 领域层
               ↘ 端口定义

Agent 工作流 → 应用能力与领域规则
基础设施实现 → 端口定义
```

领域层位于依赖方向内侧。基础设施可以依赖端口和领域数据结构，领域层不能反向依赖基础设施。

## 备选方案

### 无明确边界的单体

初始开发速度快，但模型调用、HTTP、数据库和业务规则容易混杂，难以进行单元测试、替换外部服务或解释系统设计。

### 微服务架构

可以独立部署和扩缩容，但当前规模没有足够收益，反而会引入服务发现、网络错误、分布式 Trace、数据一致性和多环境部署成本。

### 多 Agent 架构

可以把规划、预算和路线拆成不同 Agent，但会增加协调、共享状态、成本和评测难度。当前确定性规则更适合普通代码模块，不需要另一个 Agent。

### 单体框架加插件系统

扩展性较强，但第一版没有第三方插件生态需求。工具端口和依赖注入已经能够满足替换模型与旅行服务的目标。

## 影响与后果

正面影响：

- 本地开发、测试和部署路径较短。
- 领域规则可以脱离模型和外部服务进行快速测试。
- 行程版本和任务状态可以使用本地事务保持一致。
- 仍然能够通过端口替换模型、工具和存储实现。
- 架构边界适合在代码评审、简历和面试中说明。

需要承担的成本：

- 必须维护模块依赖纪律，避免单体逐渐退化。
- 长任务与普通 API 请求共享服务端资源，需要明确并发和资源隔离。
- 若未来拆分服务，需要重新定义跨进程接口、数据所有权和一致性策略。

## 重新评估条件

出现以下任一情况时重新评估本决策：

- 单个模块需要与其他模块不同的扩缩容策略。
- 外部调用故障持续影响无关业务，需要进程级隔离。
- 单体部署已经无法满足经过测量的性能目标。
- 团队扩大并形成稳定、独立的服务所有权边界。
- 出现必须独立发布且不能共享事务的数据域。
