# 需求草案

> 状态：Draft
>
> 说明：需求将在 Sprint 0 讨论后编号，并与验收标准和测试建立对应关系。

## 功能需求

### FR-001 自然语言需求理解

系统应从用户的自然语言描述中提取旅行需求，并将已识别信息转换为结构化数据。

### FR-002 最低规划信息

系统开始正式规划前，必须获得以下信息：

- 目的地城市
- 出行日期和天数
- 出行人数
- 总预算，以及预算是否包含住宿
- 兴趣偏好

### FR-003 可选旅行偏好

系统应支持以下可选信息：

- 旅行节奏
- 住宿区域
- 交通偏好
- 必去或避开的地点
- 饮食与行动限制
- 每日开始和结束时间
- 老人、儿童等特殊同行情况

### FR-004 信息补全

最低规划信息缺失或存在歧义时，系统应在正式规划前向用户追问。已经确认的信息不得重复询问，一次应集中询问少量相关问题。

### FR-005 显式默认值

可选信息缺失时，系统可以使用预设默认值，但必须向用户展示使用了哪些默认值，并允许用户修改。

### FR-006 需求变更

用户应能够修改已经确认的旅行信息。系统应保存最新确认状态，并在后续规划中使用更新后的信息。

### FR-007 结构化行程

系统应输出结构化的旅行计划，包括行程概览、每日行程、用餐安排、预算汇总、约束检查报告和信息来源。

### FR-008 每日活动信息

每日活动至少应包含时间、地点、活动内容、推荐原因、停留时间、前往方式、交通时间、预计费用、室内或室外属性以及必要的注意事项。

### FR-009 用餐安排

系统应提供用餐时间、推荐区域或餐饮类型、人均费用范围，并考虑用餐地点与前后活动的距离。无法可靠核实具体餐厅信息时，不得编造营业时间或预订状态。

### FR-010 预算汇总

系统应按住宿、交通、门票、餐饮、其他和预留金额汇总预算，并展示每日费用、全程费用、剩余预算以及未知费用。

### FR-011 约束检查

系统应检查预算、时间、路线、天气、行程强度和已知开放时间，并区分通过、警告、失败和未知状态。

### FR-012 信息来源

天气、开放时间、路线和价格等动态信息应记录来源和查询时间，并提示用户哪些信息需要在出发前再次确认。

### FR-013 局部调整

用户应能够删除或替换活动、修改预算或旅行节奏、根据天气替换活动，以及在保留其他日期的情况下只修改指定日期的行程。
