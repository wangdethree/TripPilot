# TripPilot 需求规格说明

> 状态：Accepted
>
> 候选基线：v1.0
>
> 日期：2026-07-28

## 目的

本文件定义 TripPilot 第一版的功能范围、业务边界和依赖关系。用户目标见 [产品简介](product-brief.md)，详细业务规则、数据、非功能门禁和验收依据由关联文档共同组成需求基线。

## 参与者

- 匿名旅行用户：描述、确认、查看、修改、保存或取消旅行规划
- TripPilot：维护任务状态、编排工具、生成和检查计划
- 大模型服务：执行自然语言理解与候选计划生成
- 外部数据工具：提供天气、地点、路线、价格和开放时间
- 持久化服务：保存匿名行程、版本和必要元数据

## 功能需求

### FR-001 自然语言需求理解

系统应从用户的自然语言描述中提取旅行需求，并将已识别信息转换为结构化数据。

### FR-002 最低规划信息

系统开始正式规划前，必须获得以下信息：

- 目的地城市
- 开始日期，以及结束日期或可推导结束日期的天数
- 出行人数
- 总预算，以及预算是否包含住宿
- 兴趣偏好

### FR-003 可选旅行偏好

系统应支持以下可选信息：

- 旅行节奏
- 住宿区域
- 交通偏好
- 必去或避开的地点
- 饮食与行动限制
- 每日开始和结束时间
- 老人、儿童等特殊同行情况

### FR-004 信息补全

最低规划信息缺失或存在歧义时，系统应在正式规划前向用户追问。已经确认的信息不得重复询问，一次应集中询问少量相关问题。

### FR-005 显式默认值

可选信息缺失时，系统可以使用预设默认值，但必须向用户展示使用了哪些默认值，并允许用户修改。

### FR-006 需求变更

用户应能够修改已经确认的旅行信息。系统应保存最新确认状态，并在后续规划中使用更新后的信息。

### FR-007 结构化行程

系统应输出结构化的旅行计划，包括行程概览、每日行程、用餐安排、预算汇总、约束检查报告和信息来源。

### FR-008 每日活动信息

每日时间线条目至少应包含类型、开始时间、结束时间、标题、地点、说明、推荐原因、预计费用、信息来源和必要的注意事项。活动条目还应包含停留时间以及室内或室外属性；交通、用餐和休息应作为独立时间线条目表达。

### FR-009 用餐安排

系统应提供用餐时间、推荐区域或餐饮类型、人均费用范围，并考虑用餐地点与前后活动的距离。无法可靠核实具体餐厅信息时，不得编造营业时间或预订状态。

### FR-010 预算汇总

系统应按住宿、交通、门票、餐饮、其他和预留金额汇总预算，并展示每日费用、全程费用、剩余预算以及未知费用。

### FR-011 约束检查

系统应检查预算、时间、路线、天气、行程强度和已知开放时间，并区分硬性约束和软性约束。硬性约束违反时返回 `FAIL`，软性约束违反时返回 `WARNING`，信息不足时返回 `UNKNOWN`，满足约束时返回 `PASS`。

系统处理约束冲突时应遵循已定义的业务优先级，不得自行放宽用户确认的硬性约束。

### FR-012 信息来源

天气、开放时间、路线和价格等动态信息应记录来源和查询时间，并提示用户哪些信息需要在出发前再次确认。

### FR-013 局部调整

用户应能够删除或替换活动、修改预算或旅行节奏、根据天气替换活动，以及在保留其他日期的情况下只修改指定日期的行程。

### FR-014 自动重新规划

初始计划违反硬性约束时，系统应根据约束检查结果自动调整计划并再次检查。系统最多执行 2 次自动重规划，每次必须针对上一轮的失败原因进行调整，不得原样重试或自行放宽用户确认的硬性约束。

第 3 份候选计划仍不合格时，系统应停止自动执行，进入 `NEEDS_USER_INPUT` 状态，展示未解决的问题、最接近要求的候选计划和可选择的调整建议。

### FR-015 外部服务失败与降级

天气、地点或路线等外部服务失败时，系统应返回明确的失败状态，并按照已定义的降级策略使用有效缓存、部分结果或未知状态。系统不得使用模型生成的虚构数据代替失败的工具结果。

### FR-016 匿名行程保存

系统应支持保存行程并生成不可预测的行程 ID。用户可以通过行程 ID 重新打开并继续修改行程。该功能优先级为 `Should`，第一版不提供账号注册与登录。

### FR-017 规划前确认

首次正式规划前，系统应向用户展示结构化需求摘要、显式默认值和仍然存在的不确定项，并获得用户确认。用户修改摘要后，系统必须重新校验并再次确认；未经确认不得调用正式规划流程。

### FR-018 规划任务状态

系统应使用统一业务状态描述需求收集、等待确认、规划、重规划、成功、部分成功、等待用户、失败和取消。每次状态变化必须符合已定义的转换规则，并向用户提供与当前状态一致的结果。

### FR-019 取消规划任务

用户应能够取消正在收集需求、等待确认、规划或重规划的任务。取消后系统应停止未开始的后续步骤，将任务标记为 `CANCELLED`，并且不得把不完整候选计划标记为成功。

### FR-020 地图展示

系统可以在地图上展示每天的地点、顺序和路线。该功能优先级为 `Could`，不属于第一版核心闭环。

### FR-021 导出行程

系统可以将当前行程版本导出为便于分享或离线查看的文件。该功能优先级为 `Could`，不属于第一版核心闭环。

### FR-022 删除匿名行程

启用匿名保存能力时，系统应允许持有有效行程 ID 的用户删除该行程及其版本。该功能与 `FR-016` 优先级相同，为 `Should`。

### FR-023 刷新过期来源

用户重新打开或修改行程时，系统应识别过期或时效未知的动态信息。展示历史版本时应明确标记；重新规划受影响内容时应重新查询相关信息。

### FR-024 行程版本对比

系统成功完成局部修改后，应展示版本号、修改内容、保留内容和新增警告。修改失败时不得覆盖上一可用版本。

## 约束

- 第一版只支持国内单个城市的 1～3 日自由行。
- 第一版支持 1～8 人的小团体。
- 第一版只支持人民币金额。
- 第一版只提供简体中文。
- 第一版使用中国标准时间解释日期和时间。

## 外部依赖

- 大模型服务：需求提取、澄清辅助、候选计划生成和修改
- 天气服务：天气与严重天气预警
- 地点服务：地点检索、标准化与坐标
- 路线服务：交通方式、时间和距离
- 动态信息来源：价格、开放时间和预约信息
- 持久化服务：匿名行程与版本保存

具体服务商属于技术选型，不在需求基线中固定。每类外部能力必须具有模拟实现，并遵守统一工具契约。

## 假设

- 用户会在首次正式规划前确认结构化需求摘要。
- 外部动态信息可能缺失、过期或暂时不可用。
- 用户理解行程是规划建议，出发前需要复核标记为动态或未知的信息。
- 第一版以普通城市短途自由行为目标，不处理大型团队、跨时区或复杂跨城调度。
- 第一版不保证具体商家、景点或外部服务长期可用。

## 明确不做

- 用户注册与登录
- 机票、酒店、门票和餐厅自动预订
- 真实支付
- 国外旅行和签证规划
- 复杂跨城市长途旅行
- 语音助手
- 多 Agent 协作

## 术语

| 术语 | 定义 |
| --- | --- |
| 候选计划 | 尚未完成全部约束检查的内部行程 |
| 可展示计划 | 状态为 `COMPLETED` 或 `PARTIAL` 的计划 |
| 硬性约束 | 违反后必须重规划或请求用户决策的约束 |
| 软性约束 | 违反后产生 `WARNING`，但计划仍可展示的约束 |
| 动态信息 | 天气、路线、价格、开放时间等可能随时间变化的数据 |
| 来源 | 支撑动态信息的服务商、页面和查询时间记录 |
| 局部修改 | 只针对指定日期、活动或约束的计划变更 |
| 需求基线 | 经过评审确认、作为设计与验收依据的版本化需求集合 |

## 需求变更

候选基线确认后，任何影响范围、业务规则、数据语义、非功能门禁或验收结果的变更都必须：

1. 记录变更原因。
2. 更新受影响的需求编号和文档。
3. 分析对架构、代码、测试、评测和发布计划的影响。
4. 重新运行关联回归测试。
5. 经评审后进入新的需求基线版本。
